# 架构决策记录

> 记录项目中的关键架构决策，方便后续回溯"为什么这样做"。

---

## ADR-001: 采用 LangGraph 编排多智能体
- **日期**：项目初始化
- **背景**：需要 14 个 Agent 按特定流程协作，有循环（辩论）和条件分支
- **决策**：使用 LangGraph 状态图编排，而非简单的链式调用
- **原因**：LangGraph 原生支持循环、条件路由、状态管理，适合辩论机制
- **影响**：所有 Agent 间通信通过 Graph State 传递，新增 Agent 需要注册到图中

## ADR-002: 多模型厂商适配层
- **日期**：项目初始化
- **背景**：不同 Agent 对模型能力需求不同，用户可能有不同的模型偏好
- **决策**：通过 `llm_clients/` 统一适配，支持通过配置切换厂商和模型
- **原因**：避免硬编码单一厂商，降低用户使用门槛
- **影响**：新增模型厂商需要在 `llm_clients/` 中添加适配器

## ADR-003: SQLite 作为持久化方案
- **日期**：项目初始化
- **背景**：需要存储研报、自选股、定时任务等结构化数据
- **决策**：使用 SQLite，单文件部署，无需额外数据库服务
- **原因**：本地部署场景，轻量级，零运维
- **影响**：并发写入有限，定时任务和分析任务需要串行化写入

## ADR-004: OpenClaw 作为项目协作调度层
- **日期**：2026-05-09
- **背景**：需要 OpenClaw、OpenCode、OpenCode TUI 三者协作处理同一项目
- **决策**：OpenClaw 负责任务判断和调度，不直接做代码修改；OpenCode 负责代码执行；OpenCode TUI 负责审查
- **原因**：OpenClaw 有完整的 agent 调度能力（exec / sessions_spawn / cron），适合做编排层
- **影响**：所有代码修改任务必须经过 OpenClaw 判断复杂度后决定执行路径

## ADR-005: Git 仓库 + docs/ 作为项目事实源
- **日期**：2026-05-09
- **背景**：多个工具需要读取同一套项目上下文
- **决策**：不使用任何 agent 的独立记忆系统保存项目状态，所有关键信息写入 Git 仓库的 docs/ 目录
- **原因**：避免信息分散、版本冲突、单点失效
- **影响**：每次任务开始前必须读取 AGENTS.md + docs/ 下的上下文文件

## ADR-006: 2026-07-10 将研报/半年报/昊天闭环设为唯一产品主线
- **日期**：2026-07-10
- **背景**：系统已有 TradeFlow、跟踪看板、知识库和自动开发等大量工程能力，但真实候选中仍以技术池为主，观察仓和盘后 Review 的生产记录不足，半年报事实 Provider 尚未完成。
- **决策**：优先完成 HY-002/HY-003/KB-015 及其后续事实审计，再做昊天真实候选和交易日回放；PLAYBOOK-002~006 暂停，除非直接阻塞主线。
- **原因**：用户核心目标是从政策、产业和研报中找到少量高质量中长期候选，而不是继续扩大功能数量。先验证选股和证据闭环，才能判断后续仓位规则是否值得实现。
- **影响**：自动领取顺序以 `docs/TASKS.md` 的“当前执行队列”为准；fixture 验收和真实运行验收必须分开记录；新功能必须说明是否直接服务主线。

## ADR-007: 研究评分采用四卡分层所有权，不生成混合总分
- **日期**：2026-07-13
- **背景**：现有 Tree Work 知识库、TA readiness、TradeFlow 候选分、账户风控和 PLAYBOOK 已分别存在评分或阶段字段。若各层都计算完整总分和动作，会产生重复计分、阈值冲突，以及“好公司被误判为现在可以买”的风险。
- **决策**：`research-scorer` 的代码、规则版本和正式快照写入归 ZCode 知识库接入项目所有；ZCode 发布的知识快照只拥有慢变量 `research_evidence_confidence` 与 `thesis_quality`。现有 Tree Work 页面继续作为上游知识输入，不要求历史改名。TradingAgents-AShare 不复刻评分公式，只读取版本化快照；TradeFlow 复用现有动态因子生成 `entry_timing`，账户上下文生成 `portfolio_fit`，TA 在四卡之后统一执行硬性否决并映射 PLAYBOOK 七阶段。禁止合成单一股票总分，禁止知识快照携带或覆盖交易动作。
- **原因**：证据可信度、公司逻辑、实时买点和账户资格回答的是四个不同问题；分层后才能做到来源可追溯、动态变化可解释，并让高研究分始终受行情、账户和风控约束。
- **影响**：知识库侧任务单独记录在 `docs/zcode_research_scorer_handoff.md`；本仓库新增 SCORE-001~006 消费与裁决任务线。`execution_action` 与 Buy/Risk Level 继续作为底层安全契约，`playbook_stage` 只提供更细语义。SCORE-005 可以实现不含仓位数量的阶段判定，但不解锁 PLAYBOOK-002/003 的真实三笔法和仓位拆分规则。SCORE-006 必须等真实 ZCode 快照人工确认后释放，fixture 不得冒充跨项目验收。
